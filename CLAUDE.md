## Project summary

A WPF desktop application for VATSIM Scandinavia controllers. It:

- Checks EuroScope against the pinned supported build and checks GNG, TrackAudio, VACS, vATIS, VatEFS, SAAMAN and Launchpad releases
- Applies the saved controller identity to EuroScope profiles and supported vATIS/TrackAudio settings
- Launches configured applications, shows running windows, and offers confirmed normal-close actions
- Offers optional guided setup, reviewed adoption of existing paths, and explicit client installation/update
- Reviews application removal, optional data reset and recovery exports before destructive actions
- Downloads and installs reviewed GNG ZIPs with personal-setting preservation, recovery and optional old/new-package cleanup

Target: `net9.0-windows`, WPF. Approved dependencies are Velopack for installation/self-updates and Microsoft.Web.WebView2 for the GNG browser. Keep Velopack's SDK and the local `vpk` tool pinned to the same version.

dotnet build vatsca-update-checker.sln -c Release

The project enables `IncludeNativeLibrariesForSelfExtract` and `EnableCompressionInSingleFile` when `PublishSingleFile=true`. Retain both for the distributed WPF executable. Use a fresh output directory for each package candidate.

## Architecture

```
Models/       Pure data classes. CheckResult implements INotifyPropertyChanged.
Services/     Static helpers and stateful operation services with injectable test seams; no DI container.
Converters/   WPF IValueConverter implementations.
Themes/       Light.xaml and Dark.xaml resource dictionaries (hot-swapped at runtime).
```

Windows use code-behind intentionally; do not introduce a DI container or MVVM framework. MainWindow has nine rows. The first six retain positional launch/check assignments; SAAMAN and Launchpad are selected by their management flags. Keep the remaining indices aligned when changing rows. Partial MainWindow files isolate the larger operation workflows.

`UpdateChecker` updates UI-bound `CheckResult` instances and must retain the caller's synchronization context across awaits. MainWindow invokes these methods on its UI thread; property-change observers also update the application summary directly. Only pure network helpers such as `FetchLatestTag` may opt out of context capture. `Tests/UpdateChecker.Tests` checks delayed success and failure responses with a synthetic single-thread context, without opening windows or contacting release services.

### Explicit third-party updates

`SoftwareReleaseSource` reads official VACS/TrackAudio/VatEFS GitHub metadata and vATIS's Windows feed. `SoftwareVersion` retains full prerelease ordering. `SoftwareUpdateService` coordinates explicit checks versus updates; neither construction nor checking installs anything. `SoftwareInstaller` recognizes existing installations and invokes each vendor's silent/no-restart route. The vATIS adapter must never use Setup over an existing root: that can delete profiles. Its installed helper requires a recoverable backup outside the root.

Successful parsed software catalogs are reused for ten minutes and concurrent UI checks share their request. Installer preflight uses the explicit refresh methods to revalidate current release metadata. VACS/TrackAudio/VatEFS share a GitHub cooldown within their HTTP client; SAAMAN and Launchpad retain separate service caches. This is not a global quota tracker. `VendorRequestException` carries fixed provider/failure fields and bounded retry deadlines; 403 alone is access denied, while rate-limit evidence or 429 produces a cooldown. `VendorMetadataReader` also bounds and caches public GNG/portable release pages. `LaunchpadGithubSource` overrides only Velopack's public catalog lookup, retaining its download, hash verification and explicit apply pipeline. No GitHub token is bundled or requested.

vATIS uses `https://vatis.app/downloads/windows/releases.win.json` and matching package URLs. Do not infer a published release from its source changelog. A verified vATIS executable and matching package manifest can supply the installed version even when its updater helper is unsupported; checking still shows the available version, but background updates remain disabled. Unrecognized or untrusted application identity cannot supply this fallback. Managed upgrades recognize Velopack helpers 0.0.1251 and 1.2.161, with matching product identity and Justin Shannon publisher verification. This supports beta.19 to beta.20 without replacing the locked root helper during apply. Both reviewed helpers use the same silent/no-restart command and skip the packaged Squirrel.exe when extracting the current application. Unknown helper versions require a Launchpad compatibility update; retries do not bypass the check.

Registered and executable versions must agree before a VACS/TrackAudio update. A trailing zero fourth version component is normalized (`1.4.0.0` matches `1.4.0`); genuinely different versions retain the manual fallback and its message names both values. A product-identity mismatch has a separate explanation. Checking never rewrites Windows registration to make a mismatch disappear.

`MainWindow.SoftwareUpdates.cs` binds per-row progress and serializes software updates against settings/profile dialogs and Launchpad self-updates. Download/preparation cancellation is allowed; applying is not interrupted and closing is blocked until completion. No application auto-launch is requested. Unknown layouts use a vendor-download fallback. Vendor elevation/prerequisite prompts remain possible. The synthetic `Tests/SoftwareUpdate.Tests` harness must not launch processes or read real client data; run it in CI alongside the existing self-updater harness.

Installer and client management shipped in 2.0.0, including reviewed removal/reset and discovery of existing installations. The TopSky font check shipped in 2.0.1. Release 2.1.0 adds authenticated GNG installation, list-layout preservation, old/new-package cleanup and managed VatEFS installation and updates. Full GNG package removal in the maintenance dialog remains separate from selective obsolete-file cleanup.

Release 2.2.0 adds the setup, presentation, process-control, review and activity-history improvements described below.

### SAAMAN

Stable release catalogs are cached in memory for ten minutes across normal service instances, with one shared in-flight request. Cancelling a caller does not cancel other callers. Rate-limit responses retain a bounded retry deadline from GitHub's headers; ordinary access failures are not described as rate limits. Finishing a SAAMAN action refreshes local DLL information without an online check, and an unavailable release service does not discard the installed version or saved choices.

`SaamanReleaseService` selects the highest published stable version from the bounded official GitHub release list. `SaamanInstallService` verifies asset hashes/sizes, the checksum list and static x86 plugin registration before installing the DLL. It retains licence notices in its recovery store and never loads the DLL. Fresh installation defaults to `ESAA\Plugins\SAAMAN\SAAMAN.dll`; adoption records a verified existing copy. Updates require a verified backup and recovery receipt under `%LOCALAPPDATA%\VatscaUpdateChecker\SAAMAN`. An incomplete DLL replacement blocks another update until recovery. Recovery restores a previous DLL only; fresh-install removal remains manual. SAAMAN's own LocalAppData state is not modified.

SAAMAN is controlled inline in Setup → Applications. `MainWindow.SaamanSetup.cs` handles the explicit switch, Update/Repair and selecting an existing DLL. Enabling reuses a verified local DLL or installs the stable release if missing, then applies the APP/ACC profile change. Disabling restores MAESTRO without release or runtime checks. Population does not apply changes; failed toggles retain the applied session choice. Installation skips downloading an identical version/hash/size. DLL operations acquire their own maintenance lease; profile application and explicit WebView2 preparation acquire separate leases without nesting. All mutation boundaries check EuroScope and pin filesystem paths. Cancellation is available during preparation/download only. No client is launched. Save failures keep applied choices in memory with an inline retry. Retained changes followed by a failure report a partial outcome. DLL recovery has an explicit confirmation from Activity; ordinary setup never opens a SAAMAN window.

Selecting an existing DLL is local and needs no release lookup. When enabled, selecting a moved DLL also updates its reference in the same managed profile: the previous DLL may be missing, but the current profile reference and original MAESTRO restoration state must match. The new DLL, profile and restoration state are revalidated before writing; original MAESTRO entries are retained. Target-profile migration remains separate and requires disabling the old integration first. Successful actions copy only SAAMAN choices into current settings. A save failure leaves an inline warning and Retry save action without claiming that file changes were undone.

`SaamanProfileService` shares a pure Windows-1252-preserving transformation between direct profile apply and GNG previews. `PatchSaaman` starts false; `SaamanProfileManaged` distinguishes an untouched configuration from a managed option that was disabled. The default target is exactly `ESAA APP ACC.prf`; a custom target must be explicitly selected inside the configured data folder. Enabling inserts SAAMAN first, removes SAAMAN duplicates and MAESTRO entries, and preserves other plugins' relative order and display suffixes. Disabling removes SAAMAN and restores the original MAESTRO entry, order and display permissions when Launchpad replaced it. This is a plugin-entry change, not a full-profile rollback: preserve subsequent unrelated edits and do not fabricate a MAESTRO entry if none existed. An untouched, disabled option leaves unmanaged profiles alone; normal GNG profile merging still applies.

Original MAESTRO plugin groups and ordering anchors are retained per profile under `%LOCALAPPDATA%\VatscaUpdateChecker\Saaman\ProfileState`, separately from EuroScope data and without unrelated profile content. Preview and apply validate this state's hash and the required DLLs; the saved groups remain after disabling so a later GNG rollback does not lose the restoration information.

Profile-only apply backs up and revalidates the reviewed bytes and DLL without saving controller identity fields. GNG captures the same policy in its plan, includes the exact transformed bytes in the diff, hashes the DLL dependency, and revalidates before writing. Configured DLLs and managed target profiles are protected from unrelated cleanup/removal; full GNG removal may include files proven inside its reviewed root only with a recovery export. Plugin choices are owned by Applications, separately from controller drafts and presentation preferences.

SAAMAN's static registration name/version joins the existing detailed-DLL reporting consent, including an explicitly configured external DLL. The ten-component legacy inventory shape stays unchanged. Backend enum acceptance must be deployed before releasing a client that sends SAAMAN events or detailed inventory. The synthetic `Tests/Saaman.Tests`, `Tests/Profile.Tests`, `Tests/GngUpdate.Tests` and `--check-saaman` WPF layouts cover the integration without loading plugins or starting clients.

### Existing installations and maintenance

`ControllerClientSetup` runs only from controller Save & apply and successful fresh vATIS/TrackAudio setup, never from startup, checks, launch or path discovery. It reuses the saved controller without per-client opt-in switches. `ClientSignInService` updates only identity fields in the reviewed vATIS beta.19 and TrackAudio 1.4 settings formats, preserves unrelated JSON/audio settings, and refuses running clients or unsupported versions/layouts. TrackAudio 1.4 retains existing settings schemas 2–4; Launchpad preserves that schema and seeds 4 only for a missing file. Legacy schema 1 migration remains TrackAudio's responsibility. Launchpad ratings map to vATIS enum names; its password uses the vendor's encoding. TrackAudio's own password copy is plaintext. No credentials or client JSON belong in logs, telemetry or generated evidence. The services require the caller's maintenance lease; the coordinator acquires one for the legacy wizard when needed.

`VatisSwedenProfileService` supplies the current Swedish profile from the fixed official ESAA-vATIS raw URL during those explicit setup actions. An existing profile with the canonical update URL is retained, including its local ID; vATIS performs later automatic profile updates. New downloads are bounded and schema-checked; custom/colliding files are not overwritten. Client identity and the shared airport profile stay in separate files. The current release lacks `--import-profile`, so setup writes validated configuration while the client is closed. Missing saved credentials leave existing client values in place. Client configuration failure does not turn a verified installation into a failed installation; its separate result tells the user to retry through Controller profile.

Product direction: make Launchpad the common entry point for Swedish controllers without forcing existing users to migrate. Path adoption, configuration import/reuse, software replacement and data reset are distinct decisions. A saved path enables checking/launching; it does not authorize installation or deletion. Keep the legacy/manual path useful for copies that cannot be managed safely. GNG setup has its own review and can return to the setup guide afterward.

`FreshSoftwareInstallService` and `FreshSoftwareInstallWindow` handle explicitly confirmed fresh VACS/vATIS/TrackAudio/VatEFS installation separately from upgrades. Preview selects official release metadata and validates absence, installation scope, destination and retained data; it does not download the installer. Existing copies/residue direct the user to adoption or reviewed removal. Fresh vATIS beta selection is an explicit flag, never a fake installed version; the verified Setup adapter refuses its existing root. `SoftwarePrerequisiteService` exposes separately confirmed Microsoft runtime preparation. Hold `MaintenanceLock` and block owner/dialog close until native installation completes. Reuse settings only where the vendor route permits, with verified external exports required by the plan. See [onboarding decisions](docs/product-onboarding.md).

Fresh VACS uses machine scope and requires machine WebView2; TrackAudio uses current-user scope and machine VC++ x64. Existing VACS/TrackAudio settings require export before installation. vATIS fresh setup is pinned to the reviewed beta.19 Setup and its embedded package; future releases require adapter review. Its existing-install update route instead requires a reviewed installed helper and an external backup. Accepting beta.20 updates does not broaden the separately reviewed fresh-setup or controller-configuration formats.

`VatEfsInstaller` handles fresh installation and upgrades in the standard all-users `%ProgramFiles%\VatEFS` folder. It validates the official MSI hash/size, tables and component destinations against the registered cached MSI before upgrades; custom or unknown layouts stay manual. It requires all EuroScope and `efs` processes to be absent, including at the native boundary. Upgrades first make a private verified complete installation backup under `SoftwareUpdates\VatEfsRecovery`. The signed system `msiexec` runs elevated with quiet/no-restart flags and Restart Manager shutdown/relaunch disabled. Native exit 3010 is latched before post-install checks. Synthetic tests inject the runner and registration probes; they do not establish native MSI behavior.

VatEFS fresh setup reuses the existing explicit EuroScope x86 VC++ prerequisite service because the bundled plugin imports the x86 runtime. The backend browser URL remains in `CheckResult.LaunchPath`; managed operations use its separate `SoftwareExecutablePath` (`efs.exe`). Settings retain the directory, not the executable. Installing does not silently enable the plugin in profiles. GNG/VatEFS guards never kill or launch clients, and external profile/browser settings are not part of MSI installation.

MSI commands explicitly select `IsMsi` in the native runners: property assignments quote the value (`INSTALLDIR="..."`), not the entire assignment. Ordinary CRT quoting remains for other vendor installers. `/qn` supplies MSI's quiet behavior; the process window style stays normal so unexpected diagnostics remain visible. VatEFS writes a private verbose MSI log under `SoftwareUpdates\VatEfsLogs` and reports elapsed waiting time without cancelling, killing or retrying a running installer. Logs belong to the explicit Preferences and logs cleanup option.

### Pinned EuroScope lifecycle

EuroScope has a separate lifecycle from VACS, vATIS, TrackAudio and VatEFS installation and updates. `EuroScopePolicy` is the single pinned 3.2.3.2 binary/package identity, URL and digest source shared by checks, MSI removal and `EuroScopeInstallService`. `EuroScopeInstallWindow` reviews install, repair or replacement explicitly; replacing a newer build is a downgrade and never an ordinary automatic update. Download verification and complete recovery export precede changes. Preserve installation scope/path, verify the resulting PE version as well as the three-part MSI registration, and stop for reboot/manual recovery rather than guessing after partial replacement. Unknown copies must first be resolved/adopted. See [the policy and verification notes](docs/euroscope-management.md).

The pinned MSI is unsigned and has ProductVersion `3.2.3`, while the executable is `3.2.3.2`; exact official size/SHA-256 are the package check, not Authenticode. `EuroScopeMsiFootprint` proves cached MSI identity, scope and actual component paths before maintenance. It must cover the current user's reviewed Roaming\EuroScope as well as program files and vendor-owned fonts. Repair/replacement can overwrite bundled sample/configuration files, so export the complete reviewed install/data folders first; restoring personal files remains manual and must not overwrite the new binaries. Unknown or another user's component layout is unsupported.

`EuroScopePrerequisiteService` reads the Microsoft x86 v14 runtime registration. Its separately confirmed setup route downloads only through allowed Microsoft HTTPS hosts, verifies x86 product identity and Microsoft's Authenticode publisher, and invokes `/install /quiet /norestart`. The minimum is a reviewed Launchpad baseline, not a claim about the minimum runtime required by every GNG plugin. Runtime setup is explicit and shared runtimes remain installed during cleanup.

### Discovery and setup choices

`ConfiguredPathValidationService` checks selected programs and data folders without loading binaries, launching processes, reading credentials or opening profile contents. It distinguishes optional blanks, recognised identity/layout, unrecognised custom locations and invalid selections. Bounded PE/header/version metadata inspection distinguishes client files from common installers; GNG needs matching sector files, Swedish profiles and plugin evidence rather than an `ESAA` directory alone. This is selection guidance, not publisher trust, installation-management eligibility or readiness to control.

Setup validates a selected location before saving. Changed invalid values block Save; changed warning values need an explicit checkbox. Existing missing/custom paths do not prevent unrelated preference changes. Discovery rechecks candidates before selection and again before returning them, disabling invalid results independently of their management support. The retained legacy settings/wizard types use the same program checks. Keep these checks separate from installer/removal verification, which still runs before each operation.

`InstallationDiscoveryService` reads recognized registrations and standard locations on request. `InstallationDiscoverySelection` combines discoveries with the caller's current draft, including custom/missing configured paths, and returns only explicit per-application changes. Current paths stay selected on reopening; Done with no changes is valid. Application-use preferences are independent. Setup saves reviewed changes directly, validating changed paths and requiring acknowledgement for warnings. Discovery never moves files, changes ownership/ACLs, requests elevation, launches clients or reads credentials. It cannot convert unknown/portable copies into managed vendor installations. Keep Launchpad itself unelevated; only a recognized vendor operation may request its required scope.

Changing an enabled VatEFS or SAAMAN DLL location also updates its profile references. Refreshes invalidate only checks whose configured path changed. Verified fresh-install results remain visible until a later check. Existing-client path changes go to Setup instead of reopening fresh installation. Vendor installation/removal, authentication and GNG file comparisons retain their dedicated windows. Plugin progress and failures stay inline, with Cancel reachable while other actions are disabled. GNG's secondary download/recovery options start folded; recovery and browser-fallback states reveal them.

When no GNG folder is saved, the explicit Install Swedish GNG action uses `GngSetupDestination` to prepare only `%APPDATA%\EuroScope`, with local-path and ancestor-link checks. Choosing an existing GNG folder remains separate. The normal package review follows, and only successful installation adopts the destination in settings. Cancelling may leave the empty prepared folder; it never selects that folder silently on later launches. Synthetic destination tests inject a temporary roaming root and never access real AppData.

`ControllerProfileControl` is embedded in Setup → Controller profile; `AppConfigWindow` is only a legacy wizard host for the same control. `MainWindow.ControllerProfile.cs` supplies credentials once on first visit and refreshes non-form context without replacing draft fields. Save & apply remains explicit; its result appears inline and Preview is optional. Typed per-app result lines highlight only the steps needing attention; persistence failures retain those outcomes and add a separate warning. Only controller identity fields merge into current settings after saving, preserving newer paths, preferences and plugin choices. An owner lease covers preview/save, not browsing. Failed client application or session persistence keeps the review indicator active until a successful controller save. A completed or partial settings/credential reset discards the cached draft; unrelated or cancelled maintenance leaves it intact. Pending applied plugin choices must be saved before opening removal/reset, so reloading settings cannot revert their session state. The fields use two columns when space permits and stack for narrow windows or larger text.

Activity & recovery shows the bounded local history inline, keeps selection across refreshes, and hands a chosen recovery record to the existing guarded review. Viewing history never restores files. Recovery paths are rechecked at the action boundary, and GNG restoration still requires the matching data folder, process checks and final confirmation.

`ApplicationDescriptions` shares application descriptions between setup, GNG/VatEFS help and main-name tooltips/accessibility help, without increasing compact row height. `SetupWizardState.GuideUrl` retains fixed official wiki destinations for optional guidance. Controller-profile actions check for pending GNG recovery before writing. Font checking and opening missing-font previews remain explicit actions. Installer restart requests block further installation/profile/font-preview actions in the session; this latch does not prove a Windows restart across process restarts.

Instance install/update/removal services retain that state; prerequisite operations notify the calling dialog synchronously before post-install verification. Dialogs forward it even on failure. `AppSettings.Copy()` preserves every current value/string setting across editors. `CompactLayout` defaults to true; the preferences editor changes it without altering text size or action availability. `ApplicationPreferences` stores optional Not used choices as stable application names in `NotUsedApplications`. Preferences includes VatEFS and SAAMAN as well as standalone clients; hiding them never alters EuroScope plugin choices. Filtering is reapplied when usage preferences change and when the theme redraws. Each choice is independent, so hiding EuroScope does not hide its components. Preference changes remain blocked during operations; hiding a running app does not close it. Explicitly installing a standalone client includes it again. Enabling an optional plugin also includes it; installing VatEFS alone does not enable its plugin.

### Reviewed removal and recovery

`MaintenanceWindow` separates application removal, settings/data deletion and Launchpad's own data categories. All destructive options start unchecked (Windows uninstall preselects Launchpad only). Review takes a cross-process `MaintenanceLock` until apply/cancel. Recovery exports default on and must go outside selected roots; vATIS and GNG removal require export if the user chooses to keep their settings, because those files live in the removed root. Keeping these settings means manual restoration from the export. The UI blocks closing once apply starts and reports the completed export path even after a later vendor failure.

`AtcRemovalCatalog` recognizes exact vendor layouts and scopes; `AtcRemovalVendor` revalidates identity before invoking known NSIS, MSI or vATIS uninstallers. It never executes arbitrary registry command strings. EuroScope recognition uses the official MSI identity/component path. VACS per-user operations needing elevation use a manual fallback; do not elevate them under another user's identity. VatEFS removal covers its exact configured DLL and dedicated browser profile only; other backend files and EuroScope references remain manual. Browser resets require Edge to be closed. Shared runtimes/fonts are not directly removed, but vendor-owned components (including EuroScope's font) may be removed by the vendor.

`AtcMaintenanceService` validates target overlaps, protects unselected configured paths even for missing/unsupported copies, exports before deletion, verifies each vendor's original snapshot immediately before its turn, and rechecks completed export bytes before subsequent destructive steps. It shares `PreservationPath` with Launchpad's uninstall guard to resolve existing ancestors and folder aliases during preview and apply. Launchpad removal also refuses configured ATC paths or recovery destinations within its managed installation. `RemovalFileService` uses bounded exact inventories, hashes and Windows file identity/handles; it rejects reparse paths, unsafe roots, network paths and named alternate streams (including Zone.Identifier). Direct deletion touches only reviewed unchanged entries. Exports are private file copies, not a full system/registry backup; see `RESTORE.txt`. Exact Launchpad Credential Manager targets may be deleted only by explicit selection and are never exported. Profile files and exports may already contain credentials by design.

The dependency-free `Tests/AtcRemoval.Tests` harness injects process, registry and identity probes; `Tests/UninstallIntegration.Tests` checks startup routing/registration and handoff with synthetic delegates. Neither may use the real settings, credential store or installed applications as fixtures.

### Reporting and support

Reporting, introduced in 2.3.0, uses `ReportingService` with a bounded local `ReportingClient` and atomic `ReportingStore`, without new WPF packages. Normal startup initializes it after helper/uninstall dispatch. Usage, inventory and error choices are independent and start unset; the first-use dialog preselects all three switches but only Save choices confirms them. Close, Escape and Not now leave them unset. Confirming all off is remembered. Existing stored preferences missing inventory keep it disabled. No background transmission occurs before confirmation. A manually previewed report is a separate explicit send and does not enable background reporting.

`%LOCALAPPDATA%\VatscaUpdateChecker\Reporting\reporting.json` holds a random support UUID, preferences and the bounded delivery queue. The UUID survives ordinary updates and preferences resets. Regeneration atomically replaces it, clears queued/context events and starts a new session without an old-to-new mapping. Service shutdown cancels transport and closes storage behind a local write barrier, so late HTTP continuations cannot recreate deleted data. Maintenance suspends reporting before taking a reviewed reporting-reset inventory, then resumes only in a normal owner window. Uninstall startup never initializes it. A separate reviewed reset category removes the identity and preferences; default uninstall retains them.

All outgoing fields pass the strict typed `ReportingWire` schema: enum actions/outcomes/error codes, random IDs, timestamps and numeric public versions. Never add arbitrary exception text, stack strings, paths, browser/profile contents, account identifiers or property bags. `ReportingEvents` translates known public version formats and fixed exception categories; unrecognised optional versions are omitted. Fresh activity notifications project only safe fields, not existing history or recovery paths. Setup, explicit maintenance/update operations, package source and presentation choices provide bounded usage events. Failure guards and unknown outcomes must not be counted as proven defects. Crash hooks queue best effort without changing exception handling.

Usage includes transition-only screen visits and correlated setup/maintenance attempts. Applying client sign-in details and preparing the Swedish vATIS profile have separate outcomes; neither changes a successful installation into a failed installation. Error diagnostics may include a fixed service enum and HTTP status (100–599), never a URL, header, response body or exception message. Bounded reason codes explain completed, blocked, failed or partial actions. Deploy the additive reporting schema before releasing a client that sends these fields. Dashboard operation outcomes use matched usage starts/finishes; unmatched records are incomplete coverage, not failures. Error reporting has independent consent and deduplication, so error counts are never a usage success-rate denominator. Application start requests do not prove running or connected sessions, and inventory freshness does not prove plugin loading or online status.

Usage distinguishes normal Launchpad sessions, explicit application launch actions, feature use and bounded display-preference snapshots. Showing an already running window, opening a folder, background update checks and process polling do not count as application launches. Operation IDs join start, setup steps and outcomes only within the same support identity. The usage dashboard counts distinct support IDs as observed installations, not people, and keeps error records out of usage denominators. Its 7/30-day UTC windows include today through the refresh time, marking today partial and excluding future timestamps. Returning installations overlap the preceding complete 7/30 UTC dates, subject to raw-history coverage; this is not an equal-duration growth comparison. Daily distinct counts must never be summed into weekly unique installations.

Optional inventory has a separate intake endpoint and consent. Its legacy summary retains the fixed component catalogue with known, unknown, absent or unavailable states. Configured application observations supply versions already checked by Launchpad; VatEFS uses registered MSI metadata, independently of its plugin DLL. ## Non-obvious decisions

### Windows-1252 encoding for EuroScope .prf files
ProfileService reads/writes EuroScope `.prf` files and `LoginProfiles.txt` in Windows-1252, not UTF-8. Swedish names (ö, å, ä) corrupt if read/written as UTF-8.

In self-contained .NET builds, legacy encodings are not loaded automatically. **You must call `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` before `Encoding.GetEncoding(1252)`.** This is done in `ProfileService.GetPrfEncoding()`. Never call `Encoding.GetEncoding(1252)` in a static field initialiser — the provider won't be registered yet.

### Alternating rows and theme switching

Alternating rows use `RowBackgroundConverter`, which reads `Application.Current.Resources["RowBg"]` / `["RowAltBg"]` at conversion time. `ThemeToggle_Click` resets `AppList.ItemsSource` to force reevaluation. Preserve that behavior when changing row styling.

Use `DynamicResource` for theme-dependent brushes. Keep matching resource keys and explicit menu/input styles in both dictionaries, and check live switching as well as initial rendering. The theme button shows the destination mode: `☽` in light mode and `☀` in dark mode.

### Desktop launch routes

Ordinary desktop clients, including TrackAudio, are launched through `explorer.exe` with `UseShellExecute=false`. Changes to this route need installed-client testing.

EuroScope is the exception with or without a profile. `EuroScopeLaunchService.CreateStartInfo` supplies the configured data folder as `WorkingDirectory` and uses `ArgumentList` for an optional absolute `.prf` path with `UseShellExecute=false`. With no configured data folder, it prefers the selected profile's parent, then `%APPDATA%\EuroScope`. A missing/relative configured folder or missing selected profile stops the launch; never silently substitute another folder for an explicit setting or change the process-wide working directory.

### Release selection

`SoftwareReleaseSource` requires both published, non-prerelease GitHub metadata and a stable semantic tag for VACS/TrackAudio. It validates exact asset names, HTTPS origins, size and SHA-256. Do not replace this with the generic latest-release endpoint. `SoftwareVersion` compares full prerelease identifiers; an installed vATIS beta may receive beta/stable releases, while a stable copy stays on stable. Fresh beta setup requires its separate explicit opt-in.

VatEFS includes published GitHub prereleases and labels them in the review. Its MSI requires a numeric three-part version; an unsupported newer tag blocks managed selection rather than silently offering an older release as latest. Catalog failures retain the independently read installed version. The registered package version is distinct from the DLL's plugin version.

### Read-only progress and responsive layouts

The `SoftwareProgressValue` and `SelfUpdateProgressValue` properties on `CheckResult` are read-only; their progress-bar bindings explicitly use `Mode=OneWay`. Retain this when editing templates.

The main table has equal-height rows: 36px in Compact and 56px in Expanded at standard text size. `MainWindow.Presentation.cs` applies independent 100/125/150% text preferences through shared resources and increases row height with text scale. `CheckResult` derives presentation labels without changing operation eligibility; `Tests/CheckResult.Tests` exercises status and diagnostic handling with synthetic state. The selected EuroScope profile is visible before launch. Expanded adds row explanations. Progress stays in the relevant row. Status tooltips and accessibility help retain the full diagnostic text, with keyboard copying available. There is no shared bottom details panel.

`WindowPlacementService` captures normal bounds in physical pixels, monitor name and maximized state. Restoration fits remembered bounds to an available monitor's work area; minimized state is not restored. Setup → Preferences edits `AlwaysOnTop`. `Tests/Presentation.Tests` covers pure preference, bounds and process-identity comparisons without moving windows or acting on processes. Actual monitor/DPI, focus and accessibility behavior still needs authorized desktop testing.

`ReviewSummaries` leads GNG, fresh-install, EuroScope and removal reviews with changes, preservation and recovery guidance; full plans stay expandable. Controller profile retains its existing Save & apply semantics and does not promise a backup it cannot create. `ReviewScrollHelper` positions generated reviews before confirmation; it does not confirm them. Controller-profile fields scroll independently of their footer. `ProfilePreviewWindow` receives prepared summary/masked text and a lazy reveal callback; it generates clear text only on the explicit Show credentials action and keeps it within that window. The synthetic fixture uses the same presentation class with fake values. The inert WPF fixture links production XAML and presentation models. Check both themes and minimum sizes.

## Credentials

Launchpad's saved secrets are stored in Windows Credential Manager, not in `settings.json`. `ProfileService.Apply` also writes the password into external EuroScope `.prf` files and the Hoppie code into plugin text files. Do not claim secrets are never stored as plain text; those files and backups require the same privacy as credentials. Native quiet uninstall leaves those external copies and Credential Manager entries alone. Reviewed maintenance can delete explicitly selected data/credential targets; it cannot erase unknown copies elsewhere.

| Credential target | Content |
|---|---|
| `VatscaLaunchpad/VATSIM` | VATSIM password |
| `VatscaLaunchpad/Hoppie` | Hoppie ACARS code |

Service: `CredentialManagerService` (P/Invoke on `advapi32.dll`).

`Save` checks `CredWriteW` and throws a fixed-message `Win32Exception` on failure without including the target value or secret. Controller profile catches either credential-save failure before applying any EuroScope files or returning success, keeps the entries open for retry, and warns that the first of the two independent writes may already have succeeded. These writes are not transactional; do not claim rollback or log the submitted values.

The editor uses `LoadForEditing`, which treats Windows error 1168 as a missing credential and throws for other read failures. If either credential fails to load, the form remains disabled with an explicit retry; timer refreshes never retry silently or turn a failed read into an empty replacement. Existing non-editor `Load` callers retain their previous behavior.

Controller profile distinguishes storage from file application. Its current target controls whether the button offers Save profile or Save & apply. Action acquisition cannot silently expand the scope shown when clicked. With an existing target, Save & apply updates all `ES*.prf` files in that folder, not only the selected launch profile. EuroScope must be closed; a disappearing target is rejected before profile file mutation by `ProfileService.Apply`.

A blank Hoppie code leaves existing Hoppie files unchanged in both Preview and Apply. The sync indicator still reads only the first matching `ES*.prf`; it does not establish consistency across every profile.

Missing old groups and new profiles use package defaults. Conflicting, malformed or unsafe active sources stop preservation. The off choice skips layout-source parsing and uses package settings unchanged.

The plan records the preservation choice and hashes every profile/settings input used for layout merging, including absent inputs. Preview validates the selected file's source dependencies; install rebuilds with the same choice and pins read-only dependencies that are not themselves write destinations. Exact merged bytes feed the diff, install and recovery. Settings retain incoming encoding/BOM and line endings; BOM-less EuroScope settings use Windows-1252. These parsers never read credentials from external stores or use installed profiles as test fixtures.

Each review row opens a read-only comparison in `GngFileDiffWindow`. `GngUpdateService.PreviewFile` rechecks the selected current file and package against their reviewed hashes, reads the actual planned merged profile or mapped package entry, and returns sanitized text only. Known personal files and unsupported/binary formats show metadata; text previews are bounded to 2 MiB and 20,000 lines per side before redaction. Profile sign-in fields and credential-like content are hidden. `GngTextDiff` produces bounded context hunks; the window highlights additions/removals with paired theme resources, retains textual markers and offers Next change navigation. File metadata starts collapsed for text comparisons; metadata-only explanations stay expanded. Before / After text remains available when a compact diff is too large. Comparisons never write temporary copies, log contents or change the installation plan; a failed/stale read clears installation approval and requires a new review.

`GngUpdateService.BuildPlan` verifies archive paths, size bounds, matching filename/sector generation, required package structure, profile plugin references and protected destinations. Full packages must contain referenced DLLs; Update Only can reuse unchanged installed DLLs after hashing them. Installation rechecks the plan, pins those dependencies, stages writes and backs up every replacement before changing files. Staged Updated Plugin DLLs become active package DLLs and profile references are normalized. Existing LastSession fields, supported personal preferences, Local/Hoppie files and LoginProfiles are retained; shared defaults and package references are refreshed. New profiles omit sign-in fields. Custom plugins remain unless superseded by known package entries; RDF replaces AFV/old RDF profile entries without deleting external files or silently forcing TopSky RDF preferences. Ambiguous/conflicting profiles fail review.

`GngProtectedPaths` supplies configured application locations, Launchpad storage and its installation root. Update protects the configured VatEFS DLL without blocking its entire shared plugin directory; cleanup separately protects the selected profile and configured VatEFS directory. Install and Restore acquire the shared cross-process `MaintenanceLock` internally; callers must not acquire another lease. Read-only preview does not hold it. Both mutating operations require EuroScope closed and reject linked/unsupported paths.

Installation history is under `Gng\Installations`, partitioned by canonical destination identity. The original ZIP, optional matching Full reference, originals, transaction manifest and prior receipt support recovery and later cleanup. Reference ZIP identity and bytes are rechecked before installation and when reading cached provenance; managed-plugin inventory still comes from the package actually installed. Journals are written before mutations; failure attempts rollback. Pending recovery blocks later installation and EuroScope launch, and makes the GNG version check report an error rather than infer completion from a sector filename. Restore is bound to the reviewed root and current/pending transaction; files edited afterward are retained and reported. Backups share the data volume. Verified old/new Full ZIP paths are passed to cleanup after success; missing old provenance requires explicit selection. A standalone Update Only import cannot provide a complete comparison. A paired Full reference supplies inventory, but does not prove its sector filenames/bytes were installed: cleanup retains its actual-file verification and refuses when the Full/Update Only differences prevent that proof.

`AtcMaintenanceService` treats `Gng\Downloads` as disposable downloads, `Gng\Browser` as browser sessions, and `Gng\Installations` plus `CleanupBackups` as recovery history. Download reset must not delete recovery/cache provenance. Browser-session reset checks for WebView2 processes when that session exists. `Tests/GngUpdate.Tests`, `GngBrowser.Tests` and `WebViewRuntime.Tests` use synthetic data/delegates by default; they do not authenticate or install runtimes. The browser harness runs the exact selection scripts against a synthetic DOM using Node.js 20 or later, without npm dependencies. Real authenticated page layouts, identity-provider compatibility and installed plugin behavior remain interactive validation boundaries. See [user guidance](docs/gng-updates.md).

## GNG cleanup

`GngCleanupWindow` is opened after a GNG installation or from Setup → Swedish GNG. Its destination is the reviewed EuroScope data folder, shown read-only. It takes two original complete AeroNav ZIPs after the new package has been installed, optionally prefilled from verified installation caches, offers an unchecked preview and asks before archiving or restoring. This dialog itself does not download or install GNG. `MainWindow.GngCleanup.cs` stops the process timer during the modal dialog and supplies protected configured application paths, Launchpad installation/data and Launchpad recovery locations. Other operations and closing the owner stay blocked through `ShowOwnedDialog`.

`GngCleanupService` verifies complete package identity and newer generation ordering, installed replacement sectors, byte equality of retired package files and references from local profiles/radar screens. Missing or external profile/screen references stop cleanup when their dependencies cannot be verified. It includes local runway settings only when matching retired SCT/ESE files prove their generation. Unknown, modified, referenced, staged and protected files remain. Preview does not mutate files; archive rebuilds the plan, verifies unchanged ZIPs/files and checks that EuroScope is closed. Selected files, replacement sectors and required retired companions remain locked against changes throughout archiving. Archive and restore acquire the shared cross-process `MaintenanceLock` internally; callers must not acquire it a second time.

Cleanup moves files into `%LOCALAPPDATA%\VatscaUpdateChecker\CleanupBackups` on the same volume. It writes a recovery manifest before moving and verifies hashes through Windows file handles while preserving identity. Restore accepts a direct child of that backup folder only and requires the manifest's original root to match the current reviewed data folder. It verifies paths/hashes, protects configured applications and never overwrites an existing destination. Results include completed files, skipped reasons and the recovery folder, including partial completion. Junctions, symbolic links and unsupported layouts fail closed; Windows short names are resolved before comparisons. See [user guidance](docs/gng-cleanup.md).

`Tests/GngCleanup.Tests` uses synthetic complete ZIPs, profiles and isolated storage/process/lock delegates. CI runs comparison plus archive/restore cases. The inert UI fixture links the cleanup XAML with synthetic rows; it never links the cleanup service. Neither fixture establishes behavior with a user's real package or native EuroScope session.

## Logging

`Logger` appends timestamped entries to `%APPDATA%\VatscaUpdateChecker\launchpad.log` and suppresses logging failures. Above 200 KiB it retains the latter half of the current lines; it does not enforce a fixed 500-line limit. Callers must omit credentials. File paths and error messages can still contain private details, so keep raw logs out of shared documentation.

## Recent activity and recovery

`ActivityHistoryService` records explicitly requested application installation/update, GNG installation/restore/cleanup, and removal outcomes under `%LOCALAPPDATA%\VatscaUpdateChecker\Activity\history.json`. It stores bounded enum values, timestamps, public version metadata and local recovery/data-folder paths; never pass profile contents, credentials or raw exception messages. The store retains at most 100 entries/512 KiB, uses a cross-process file lease and atomic replacement, and preserves unreadable history instead of overwriting it. A history-write failure cannot change the underlying operation's result and is visible in the main Activity notice.

Records distinguish completion, cancellation, stopped work and partial outcomes needing attention. They describe the outcome at that time, not current installed state or proof that a requested Windows restart happened. `ActivityWorkspaceControl` requests verified local recovery directories from its MainWindow owner; vendor recovery remains manual. Its GNG handoff passes the selected backup as a chooser suggestion to the existing install/cleanup restore dialog. Pending installation recovery has priority. It does not perform a restore, acquire a nested maintenance lease, bypass process checks or skip final confirmation.

Preferences/logs reset includes activity history; recovery backups remain a separate selection. `AtcMaintenanceService.ActivityHistoryReset` reflects actual history removal during the direct-deletion stage, including partial deletion. A failed operation before that stage can still be recorded. Once history is removed, maintenance does not immediately recreate it with a reset record, and the in-memory write-failure notice is cleared. `Tests/ActivityHistory.Tests` exercises bounded storage, malformed input, outcomes and recovery-path validation using temporary synthetic files. It does not read the user's history or open recovery folders.

## Validation boundaries

The workflow lists the current console harnesses, including `Tests/Presentation.Tests` and `Tests/ActivityHistory.Tests`, and the hidden WPF layout check. Their defaults use synthetic files/state; inspect a harness's README before using optional native signature or package-inspection modes. `Tests/UiReview` links production XAML and presentation models to inert handlers. It checks layout/bindings, not the real dialogs' native operations.

Run the explicit Release build and relevant harnesses for a change. Synthetic checks do not establish installed update/restart/uninstall behavior, UAC/scope, recovery or desktop accessibility/DPI. Native testing needs separate authorization and an isolated environment; keep its plans and results local.
